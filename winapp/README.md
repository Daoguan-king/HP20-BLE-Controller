# HP20 加热台 Windows 蓝牙上位机

正点原子 HP20 加热台的 Windows 桌面上位机：Python 3.12 + [bleak](https://github.com/hbldh/bleak) + Tkinter。
自带**进程内模拟设备**，无硬件即可跑通全流程；模拟设备的参数与应答形状都对齐真机实测。

依据：A1 逆向产物（`protocol/hp20_commands.json` + `docs/hp20_protocol.md`）
+ **真机实测标定**（2026-10-17，HP20 / AA:BB:CC:DD:EE:FF）。**两者冲突时以实测为准**，
文档值保留在常量/注释里可回溯。`test_commands.py` 逐字节比对 JSON，`test_real_frames.py` 固化真机抓包。

## 安装与运行

```powershell
# 依赖：Python >= 3.10（验证 3.12.14）+ bleak（验证 3.0.2）；tkinter 为标准库
& 'C:\Users\Administrator\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\python\python.exe' -m pip install bleak
```

```powershell
python atk_hp20.py --sim            # 模拟设备，无硬件跑通全流程
python atk_hp20.py --scan-only      # 只扫描（地址在首列，可直接喂 --address）
python atk_hp20.py                  # 真实 BLE：扫描 → 选中 → 连接
python atk_hp20.py --address AA:BB:CC:DD:EE:FF   # 已知地址直连（推荐，见连接排障）
python atk_hp20.py --name HP20                   # 按广播名查找
python atk_hp20.py --probe AA:BB:CC:DD:EE:FF   # 无 GUI 真机只读自检（绝不写；0/1/2）
python atk_hp20.py --selftest       # 非 GUI 端到端自检（模拟设备），退出码 0 = 通过
python atk_hp20.py --sim --smoke 5  # 起窗口跑 5 秒自动关闭并打印结论
```

参数：`--timeout`（命令应答超时, 默认 **2.0s**）、`--connect-retries`（连接退避重试次数, 默认 4）、
`--gap`（写间隔 0.015）、`--poll`（轮询 0.125）、`--retries`（命令超时重试, 默认 0）、
`--dev-id`/`--family`（0x09/0x02）、`--csv`、`--log`。

## 诊断详情面板（只读）

「设备 → 诊断详情」是给报障/复现用的只读快照，**发送与接收各占一段、互不覆盖**（各自的最后一帧 +
   各自的时间戳 `TX→设备` / `RX←设备`；某段还没数据时显示占位文案）：

1. **字节带**：索引行 + 字节行，**每行 32 字节**（HP20 实际帧最长 26 字节，一律单行；超过 32 才折行），
   等宽列对齐（中文按 2 格算宽度）；不按窗口宽度动态计算 —— 复制出来的文本要能逐字比对；
2. **字段解析表**：`偏移 | 长度 | 字段 | 类型 | 原始字节 | 解码`，一个字段一行，
   天然支持跨字节字段。按命令选 schema：帧头 `SOF/设备头/cmd/len`、尾部 `LRC`（`ok` 或
   `错（应为 0x??）`）；`0x00` 型号、`0x03` 设温（index+温度）、`0x04` 四预设、`0x05` 挡位、
   `0x06/0x07` 回流 8 字段、`0x08/0x09` 蓝牙名、`0x0A` 状态（温度/供电/输入电压/输出状态/
   输出功率/W1 目标挡位模式/W2 64 进制计时）、`0x0B/0x0C` 维修 8 字段；**未知命令只给字节带 +
   「未知命令 0x??」，不硬解 payload**；
3. **计数**：TX/RX、超时、重试、忙拒、空应答、丢帧、重连（成功/尝试）。

**第三段：钉住选中的帧**（T 阶段）——在「原始帧控制台」里单击一条帧行（单击即选中整行，
或拖选同一行）后点 **`解析选中帧`**（双击该行等价），面板最上面会多出一段
`选中的帧（来自原始帧控制台  方向  时间）`，同样走 `framediag`（字节带 + 字段表）；
这一**只由用户操作改变**：轮询刷新、`自动刷新`、`清空`（清最近收发）都不动它，
只有 `清除选择` 会把它整段去掉（不留空标题）；`复制全部` 在它存在时会一起复制。
若日志行不是完整帧（SYS 说明行、被折开的续行）→ `解析选中帧` 置灰并提示「请选择一条完整帧」；
记录本身不足 6 字节时该段显示「该记录不是完整帧」而不是崩。

刷新策略：最多 **2 次/秒**重写（状态帧 125 ms 一帧，逐帧重写会跳滚动位置）；重写前后保存并
恢复 `yview`；面板不在当前页时不重写、切回来补刷；`自动刷新` 关掉后只能点「刷新一次」。
`复制全部` 复制本文（发送段 + 接收段 + 计数），`清空` 清掉两段的最后一帧。

> R 阶段的两处删除：用户反馈「原始收发（最近 50 条）」与「原始帧控制台」重复、且是滚动乱跳的主因，
> 已删除；面板开头那行 `W2 = 0x… 低6位 … 次7位 …` 也按用户要求删除（原值改由字段解析表承载）。
> S 阶段两处修正：只跟「最近一帧」会让 TX/RX 交替占位、面板来回闪 → 改成发送/接收**各留一帧**；
> 字节带从 16 字节/行改成 **32 字节/行**（17 字节的 RX 帧不再留半行）。

## 「不加热」归一化与主界面显示（V 阶段）

实测设备停在待机/设置界面时仍会把 `payload[5]` 报成 `0x02`，功率与目标字段也可能是残留值。
因此统一判据（`hp20_commands.is_heating`）：

```
不加热  <=>  mode ∈ {0 待机, 3 设置, 8 主页}  或  payload[5] == 0x00
加热中  <=>  其它（mode 1 回流 / 2 加热 / 4 维修 且 [5] == 0x02）
```

- **输出状态**：不加热显示「待机」；加热中按 mode 显示「加热模式运行中 / 回流焊运行中 / 维修模式运行中」。
  原始 `payload[5]` 不变，诊断面板仍显示 `[5]=0x02` 原值；
- **功率**：不加热一律按 0 处理（`effective_power`）—— 大字的当前功率、功率占比进度条、折线图功率曲线、
  悬浮框、CSV 的 `输出功率(W)`/`功率占比(%)` 全部走同一口径；加热中才用 `[6]` 原值；
- **目标温度曲线**：不加热时不画，也不计入 Y 轴量程（只画实测温度）；设备残留的目标值仍显示在「目标温度」大字里；
- **开始加热**：命令下发成功但当前不加热时，状态栏用**橙色警告**提示
  「已下发到设备（注意：设备当前在待机/设置界面，可能不会开始加热；请先切到加热界面）」，
  不再一律报「成功」；按钮不禁用（mode 是设备上报的，禁用会在异常态把用户卡死）。

### 时间轴与导出

- 折线图 **X 轴改为真实时间**（`chart.time_ticks`/`x_time`/`hit_time`）：跨度 < 60 s 显示 `MM:SS`，
  ≥ 60 s 显示 `HH:MM:SS`，4~6 个刻度；样本不足 2 个或同一时刻显示 `--:--`；
  悬浮框/十字准线按**时间最近**取样（不再按样本序号，轮询间隔变了也不会画歪）；
- 监控页新增 **「保存图表」**：弹保存对话框（默认 `hp20_chart_YYYYmmdd_HHMMSS.png`），
  用 Pillow **离屏重绘**（2 倍尺寸、200 DPI、含坐标轴/图例/标题：设备名 + 时间范围），不截屏；
  Pillow 不可用时自动改存 SVG 并提示；无数据时只给提示、不写空图。

### 重置默认参数（回流焊 / 维修）

两页各有一个「重置默认参数」按钮（带确认对话框），按手册出厂值写回并**读回比对**：

| 页 | 8 个字段（cmd 0x06 / 0x0B） |
|---|---|
| 回流焊 | 预热 150℃/120s，恒温 180℃/90s，回流 260℃/60s，冷却 80℃/300s |
| 维修 | 除胶 100℃/120s，分层 80℃/120s，贴合 80℃/120s，植球 260℃/120s |

常量在 `hp20_commands.REFLOW_DEFAULTS` / `REPAIR_DEFAULTS`（单一来源），下发前照样走
`validate_fields`；结论三态：`已重置并读回确认` / `读回不一致，请检查（写入 X，读回 Y）` / `读回失败`。

## 界面信息分层（O 阶段整理）

主界面只放**用户会看、看得懂**的数值：温度、目标、模式、供电/输入/输出功率、计时、功率占比。
所有字段偏移、位运算、协议解释、内部原值都收进**「设备 → 诊断详情」**：

| 曾经出现在主界面 | 现在 |
|---|---|
| `当前温度 payload[0:2]` / `目标温度 W1&0x3FF` | **当前温度** / **目标温度** |
| `模式 · 挡位` | **模式** |
| `风扇 不可读（固件不上报）` | 删掉（结论保留在诊断详情与本 README） |
| `W2=0x051B` 原值 | 移到「设备 → 诊断详情」的字段解析表（`W2 计时（64 进制 MM:SS）` 一行，含原始 hex 与 `0x…=十进制`） |
| 长说明「计时 = W2 的 64 进制打包…」/「风扇：面板 1~5 档不上报…」 | 移到「设备 → 诊断详情」 |
| `温度(0:2) 50℃ / 目标 50℃ / 输出 11W / 样本 400` | `样本 400 · 供电 140W · 输入 27.8V · 输出 11W` |
| CSV 下拉 `简洁 CSV（对齐手机 APP）` | **简洁**（说明移到旁边一小行灰字） |

CSV 的**开始/停止 + 格式选择**放在实时监控页图表下方；底部状态栏只留一行摘要
（`CSV: 未记录` / `CSV: 记录中 → 文件名`）以及 `轮询 0.125s · 写间隔 0.015s`。

**轮询/写间隔输入框**（O 阶段 bug）：之前只有 ▲▼ 生效，手输（含 Enter）不生效。
现在 `<Return>` 与 `<FocusOut>` 都会提交，走纯函数 `parse_interval(text, lo, hi)` 校验
（轮询 0.05~5.0 s、写间隔 0~1.0 s），非法值**回退显示当前生效值**并提示，生效后同步刷新底部状态栏。

## 参数补读（`auto_refresh_params`，默认关闭）

旧实现照抄官方 APP 的「W2 变化 → 补读 0x04 + 0x0C」。但 **W2 在计时状态下每秒都变**，
于是每秒补读两条参数并弹一次「维修参数已读回」，界面直接卡顿。

现在：
- `auto_refresh_params` **默认 False**：用户没点读取，程序绝不自动发 0x04/0x0C；
- 如需该能力，触发条件收紧为 **mode 变化**（不是 W2），且内部读取标记 `silent`——
  只更新控件，不写用户可见提示；
- 有用例守着：连续变化的 W2（0x0087→0x0083）在任何配置下都不产生 0x04/0x0C。

## 「开始加热」的正确顺序（H 阶段真机 bug 修复）

**`0x05 [挡位]` 会把目标温度改写成该挡位的预设值**。所以顺序必须是：

```text
AF 09 02 05 01 00 40   (0x05 [0] 选 T1 -> 目标自动变成 T1 预设，例如 66℃)
AF 09 02 03 03 04 46 00 F6   (只有需要自定义目标时才追加 0x03 index=4 70℃，覆盖预设)
```

- `start_heating(channel, target_c=None)`：先发 0x05；`target_c` 非空且**不等于该挡位预设**时才补 0x03；
- 若先发 0x03 再发 0x05，用户输入的目标会被预设**覆盖吞掉**（旧实现的 bug）；
- 界面：选中挡位即回显该挡位预设（如「T1 预设 66℃」），勾选「自定义目标」才用输入框的值覆盖。

## 「停止加热」怎么实现（U1 已由真机实测解决）

协议里**没有**独立 stop 命令。实测有两条等价路径，界面默认走第一条：

**① 默认（推荐）：选 T4 停止通道** —— 官方 APP 只有 T1/T2/T3 三个挡位，T4 是隐藏的第 4 挡、
预设固定 0℃；选它后目标温度变 0℃、停止加热，**设备面板会显示 T3**。

```text
AF 09 02 05 01 03 3D      (cmd 0x05, channel=3 / T4)
```

**② 备用：把 T5 目标温度设成低于当前温度（用 0℃）** ——

```text
AF 09 02 03 03 04 00 00 3C   (cmd 0x03, index=4/T5, temp=0)
   -> 功率立刻 6 → 0，温度 60 → 59 → 58 开始下降
```

所以界面：
- **开始加热** = 先发 0x03 设 T5 目标温度，再发 0x05 [挡位]（挡位是界面选择的 T1/T2/T3），
  两次事务各自遵守 15 ms 写间隔与单命令在途；
- **停止加热** = 默认发 0x05 [3] 选 T4，并记日志；停止后状态里的**挡位字段 = 3（T4）**、目标 0、功率 0
  （设备物理面板显示 T3）；**恢复加热要再发 0x05 [0] 重新选挡**；备用路径 0x03 index=4 置 0℃ 保留；
- 两条都是**实测得出的等价做法，不是协议里的独立命令**，也不等于切换设备运行模式；
  **设备物理面板按钮仍是最终保障**。

## 真机实测修正（与 APK 文档不同）

1. **GATT 不同**：真机 service `fff0`，`fff1`[notify, write-without-response] 收发同用，
   `fff2`[notify, read]，`fff3`[write-without-response]。APK 的 `ff01/ff02/ffff` 真机不存在。
   → 不按 UUID 写死：遍历全部特征，RX 取第一个带 notify/indicate 的，TX 取第一个带 write 的
   （优先 write-without-response）；缺失时打印**完整特征表**并明确报错。
2. **识别应答的设备头是 `FF FF`**：`AF 09 02 00 00 46` → `DF FF FF 00 02 09 02 16`。
   型号只看 **payload 前两字节 == 09 02**；帧头既不参与型号判定，也不参与请求-应答配对（只比 **cmd**）。
3. **写命令应答带 1 字节 payload**（如 `DF 09 02 03 01 00 12`）：判据 = 同 cmd + payload 非空。
4. **payload[0:2] 才是当前温度**（文档写 [3:5]）；[3:5] 恒 200，是诊断值不是温度。
5. **mode 实测 0=待机 / 2=加热模式**（文档「0/1=加热、2=回流」不成立）；mode=2 时功率可以是 0
   （保温/不加热），所以文案不写「加热中」。`(W1>>10)&3` 是挡位 T1..T4。
6. **命令应答超时提到 2000 ms**：真机部分应答延迟 0.7~1.5s，1000 ms 会误判超时。
7. **扫描扫不到 ≠ 设备离线**：见的设备不在广播里也能连上（系统缓存地址 / 直连），故连接改三段式（下节）。
8. 设备纯轮询、无主动推送。

## 实时状态字段（实测语义）

payload 11 字节（整帧 17 字节）：

| 偏移 | 类型 | 含义 |
|---|---|---|
| [0:2] | i16le | **当前温度**（实测唯一真实温度） |
| [2] | u8 | **供电功率 W**（换电源前 65 → 140W 电源后 140；手机顶栏「65W」即此字段；加热实测 125W / 135W，与 140W 电源相符） |
| [3:5] | i16le | **输入电压 ×0.1V**：200 → 20.0V、278 → 27.8V；带载时 27.9V → 27.1V（≈4.6A @125W；**不是温度**） |
| [5] | u8 | **输出状态**：0x00 待机 / 0x02 加热模式运行中（保温、功率 0W 时也是 0x02 → 表示「模式在跑」而不是「正在出功率」；其余显示「未知(0xXX)」，原值字段 `output_state_raw`） |
| [6] | u8 | **当前输出功率 W**（实测 0 / 6 / 11 / 56 / 58）；% = `[6] / [2] × 100`（手机「9%」= 6/65 验证一致） |
| [7:9] | u16le | W1：目标温度 `&0x3FF` / 挡位 `(>>10)&3`（T1..T4，**停止后为 3**）/ 模式 `(>>12)&7`（0 待机, 2 加热模式 —— **全程恒为 2，功率 0 时也是 2**） |
| [9:11] | u16le | W2 = **64 进制打包的 MM:SS**：MM=(W2>>6)&0x7F、SS=W2&0x3F，每真实秒 -1；**SS>=60 表示计时未开启 → OFF**（0x29BF 的 SS=63 即如此）。决定性锚点：设置 25 min → W2=**1600**=25×64 → `25:00`；20 min → **1280**=20×64 → `20:00`；1229 → `19:13`、1832 → `28:40`。标签随模式：回流焊/加热/维修→「加热时间」，待机/设置/主页→「休眠倒计时」。设备本地设置，**协议没有读写命令** |

**模式枚举**（以用户手册为准）：

| mode | 含义 | 挡位/阶段字段 (W1>>10)&3 |
|---|---|---|
| 0 | 待机 | 上次挡位（显示字段值） |
| 1 | **回流焊** | 阶段 PH 预热 / SK 恒温 / RF 回流 / CL 冷却 |
| 2 | **加热** | 通道 T1..T4（T4 是隐藏的停止通道） |
| 3 | 设置 | 未知（显示字段值） |
| 4 | 维修 | **除胶(Debond) / 分层(Delam) / 贴合(LAM) / 植球(Reballing)**（用户真机在面板上确认，U4 结案） |
| 8 | 主页 | 显示字段值 |

> ⚠ 官方 APP 的 `stateStr` **把 1 和 2 的字符串表写反了**（cf==1 返回 T1..T4、cf==2 返回 PH/SK/RF/CL）。
> 本实现按手册（1=回流焊、2=加热），并有测试专门断言「mode=1 的 slot 必须是 PH/SK/RF/CL，不能是 T1」。

真机帧样例（`test_real_frames.py` 固化）：

```text
识别   TX AF 09 02 00 00 46            -> RX DF FF FF 00 02 09 02 16
写 ACK TX AF 09 02 03 03 04 1E 00 1E   -> RX DF 09 02 03 01 00 12
状态   RX DF 09 02 0A 0B 23 00 41 C8 00 00 02 FA 0C B2 04 17
        = 当前温度 35℃ / 额定 65 / 诊断 200 / 功率 2 / 目标 250℃ / 挡位 T4 / 待机 / W2=0x04B2
```

**时序**：轮询 125 ms、命令超时 2000 ms、等待粒度 10 ms、写间隔 15 ms、**单命令在途**、
写前暂停轮询、连接后 1 s 再握手。连接/重连退避：**1 / 2 / 4 / 8 s，最多重试 4 次**。

## 连接链路：三段式（真机实测要求）

「扫描扫不到」不代表连不上，因此每次连接/重连按顺序尝试三段，**每段独立超时**，
三段都失败才进入退避：

1. **① 按已知地址查**：`BleakScanner.find_device_by_address(addr, timeout=6)`（走系统缓存）→ 连接；
2. **② 直接连接**：`BleakClient(address)`，超时 15s → 连接（不需要广播/缓存）；
3. **③ 重新扫描**：6s，按名/按地址匹配后再连。

真机实测：①常常空等满 10s 仍失败、②约 18s 才成功，所以默认值收成 **6 / 15 / 6**；
每段切换都会把「连接中 · ①按地址查找 / ②直接连接 / ③重新扫描」写进状态栏与连接诊断页。

重连时**从上次成功的地址开始**（记住 `last_address`），因此掉线后通常第 ① 段就恢复。
界面的「重新扫描并连接」按钮走同一套三段式。

## 连接排障

1. **扫不到设备**：先直接 `--address <地址>` 或界面「重新扫描并连接」——三段式里前两段都不依赖广播。
   若三段全失败，状态栏/诊断页显示「设备未广播：可能正被手机 APP 占用，或已进入休眠/断开电源……」。
2. **连上但中途 Not connected**：后台自动重连（退避 1/2/4/8 s，最多 4 次），成功后再握手识别并恢复轮询；
   UI 显示「重连中(第 n/4 次)」，可随时「取消重连」。
3. **同一台设备不要多人同时连**：BLE 从机会被占用，第二方连接会让先连的一方掉线。
4. **命令偶发超时**：默认 2000 ms；仍超时会记「应答超时」，可调 `--timeout`。
5. 应答抖动时不要猛点按钮：写命令是单命令在途，忙时会被拒绝并记日志。

## 计时编码的定论（N 阶段，反转了两次）

`W2` 是 **64 进制打包的 MM:SS**（每分钟 **64** 个单位，每真实秒 -1），**不是 60 进制、也不是总秒数**。
官方 APP 的 `heartTimeStr` 就是这么多，之前的「按秒数换算」是错的。

决定性锚点（用户口述设置值 vs 帧内原始值）：

| 设置 | 原始 W2 | 64 进制解码 |
|---|---|---|
| 加热超时 25 min | **1600** = 25 × 64 | `25:00` |
| 休眠时间 20 min | **1280** = 20 × 64 | `20:00` |
| 20 min 倒计时途中 | 1229 | `19:13` |
| 30 min 设置途中 | 1832 | `28:40` |
| 计时未启用 | 0x29BF（SS=63） | `OFF` |

两个设置值精确等于「分钟 × 64」，不可能是巧合。**SS>=60 即 OFF**，这正是官方 APP 的哨兵判定。

实现：`format_timer(w2)` → `MM=(w2>>6)&0x7F`、`SS=w2&0x3F`，SS>=60 返回 `OFF`；字段名 `timer_packed`（打包值，不是秒）。
注意 `SS=60..63` 是非法秒：真机会不会经过这 4 个值未实测，**模拟设备**按「设备不显示非法秒」处理（跨分钟直接跳到 59 秒）。

## 连接总预算（M 阶段新增）

三段式 + 退避全跑满会到 90 s 以上（真机实测一次 **94.5 s**），用户只能干等。
现在 `ConnectionManager` 有 **总预算 45 s**（`DEFAULT_TOTAL_BUDGET_S`）：

- 每段超时都按「剩余预算」裁剪（`min(段超时, remaining)`），并用 `asyncio.wait_for` 硬钉住总耗时；
- 预算用完就停手，发 `give_up` + 可操作提示：
  **「设备未响应：可能正被手机 APP 占用，请关闭手机蓝牙后重试。（本次已用 Xs，超过 Ys 预算，已停止重试）」**；
- 界面在等待期间每秒刷新 `②直接连接 … 12s`（`progress_text()`），让用户看到在动；
- 用例：`NeverTransport` 三段全失败 → 断言耗时 ≤ 预算、事件序列含 `give_up` 与该文案、每段超时被裁剪。

## 连接按钮状态机（L 阶段 bug 修复 + 可取消）

断开或连接失败后必须把「连接」恢复可用，否则用户被锁在「点不了」状态。
状态由纯函数 `link_button_states(connected, connecting)` 决定：
已连接 → (连接 disabled, 断开 normal)；**连接中 → (连接 normal，文案变「取消连接」, 断开 disabled)**；
其余（未连接/断开后/扫描完成）→ (连接 normal, 断开 disabled)。

**连接中可取消**（用户反馈：连错设备只能硬等 45s 总预算走完）：
点「取消连接」→ 中断当前正在等待的那一段（①查找 / ②直连 / ③扫描都算）→ 释放 BLE 客户端
（`transport._cleanup()`）→ 状态回「未连接」→ 按钮恢复「连接」，**不触发自动重连**，
可以立刻重新扫描/连接；状态栏给出「已取消连接（耗时 Xs）」。

## 未确认项（含风扇）

- **风扇完全不上报**：面板 1~5 档风速是固件本地量，状态帧里**没有任何风扇信息**。
  曾把 `W2 bit13` 当"是否运转"，已用同一次会话的三组帧证伪（保温 0x04C5 / 加热 0x04C3 / 恢复 0x04C1
  的 bit13 全为 0，而风扇确实在转）；唯一 bit13=1 的样本全是 `W2=0x29BF`（加热超时未启用的哨兵常量）
  本身第 13 位为 1。界面因此只标注「风扇 不可读（固件不上报）」，不做任何派生。
- **计时**：W2 是 64 进制打包（见上一节）。它是设备本地设置，协议没有读写命令，界面数值可能滞后于面板；
  `SS=60..63` 的取值在真机上是否出现仍未实测（官方 APP 与我们都会显示 OFF）。
- **风扇**：`W2=0x29BF` 是「加热超时未启用」的哨兵常量，它的第 13 位曾被误当风扇位——
  已证伪（见上）。界面不再显示风扇状态，只写「不可读」。

| 编号 | 项目 | 本实现的处理 |
|---|---|---|
| U1 | 没有独立 stop 命令 | **已由实测解决**：停止 = 目标温度置 0（见上），按钮已启用 |
| — | W2 bit14「单位位」 | 真机从不置位 → 单位固定 ℃，bit14 仅诊断 |
| U7 | mode 其余取值（文档 4=维修、8=主页） | 只映射实测 0/2，其余显示「未知(n)」；保留 `mode4` 诊断 |
| — | 协议无「启动回流/启动维修」命令 | 界面只同步参数；挡位/计时从实时状态读回 |
| — | 停止加热是否等价于「切换模式」 | 不等价：只把目标压低，设备模式不变（实测 mode 仍为 2） |
